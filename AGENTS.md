# work-fold contributor guide

work-fold is a local-first Electron shell around ordinary folders and the native Pi agent runtime. Read [the product model](docs/product-model.md) before changing navigation, terminology, storage, trust, or Assistant behavior, read [the App platform foundation](docs/app-platform-foundation.md) before changing App Project, release, instance, Feature, publication, hosted-runtime, data, connection, automation, or broker semantics, read [the management layer](docs/management-layer.md) before changing the kernel, CLI, task registry, or an agent-facing adapter, read [Checks](docs/checks.md) before changing Check declarations, sensors, targets, evidence admission, decisions, or run authority, and read [the fold](docs/fold.md) before changing the fold's verb ledger, prepared acts, Recently deleted (the trash), routings, the glance, or published viewer pages, read [Receipts, not gates](docs/receipts-not-gates.md) for the 2026-09-10 authority decisions the fold register now carries, and read [the collaboration contract](docs/collaboration-contract.md) before changing durable requests, delegation, questions, results, waiting and continuation, or an app's owned-change hints. These documents record the shared product and control-plane direction; update them when those decisions change.

## First visit

- Start with [Contributing](CONTRIBUTING.md) and the [development guide](docs/development.md) for setup, a source map, development profiles, and the right verification lane.
- Use Node 24 for the contributor/CI lane (`.nvmrc`). Run `npm ci`, then `npm run repo:check`; the latter also works before installation and never needs credentials or a network connection.
- `npm run local:dev` starts the browser UI and local API; `npm run desktop:smoke` starts unpackaged Electron after preparation. Use disposable folders for live work. The development app profile is separate, but Pi resources and Keychain require their own consideration; follow the development guide for explicit isolation.
- `npm run check` includes repository hygiene and TypeScript checks. Keep new shared Skills, Claude symlinks, links, and documented npm commands valid; do not copy shared policy into a harness-specific file.

## Harness parity

- This `AGENTS.md` is the one canonical contributor contract. Codex reads it directly; Claude Code reads the root `CLAUDE.md`, which imports this file with `@AGENTS.md`.
- Edit shared policy here instead of copying it into `CLAUDE.md`, `.claude/`, `.codex/`, or harness-specific prose. Keep the root Claude entrypoint thin so the two harnesses cannot drift.
- Project-wide Skills have one source under the tracked `.agents/skills/` directory. Codex discovers that source directly; Claude Code gets the same Skill through tracked `.claude/skills/` symlinks. Never copy Skill contents between the two trees. All other `.claude/` and `.codex/` files are machine-local harness state, not contributor contracts.
- Both harnesses use the same checked-in npm scripts, documentation, test suites, and release lanes. Do not create alternate Claude-only or Codex-only build or release commands.
- Native full-trust Skills, Extensions, built-in tools, and their catalog/runtime remain Pi-owned. work-fold owns the product documentation and restricted-app lane, but both remain harness-neutral. Do not create a Codex-only or Claude-only catalog, wrapper format, prompt copy, or tool policy.
- `work-fold <command> --json`—for example, `work-fold context --json`—is the stable installed-product surface for any shell-capable harness: a content-free read lane plus a per-launch-authenticated act lane (`chat`, `chats`, `history`, `files`, `search`, `library`, `spaces`, `tools`, `apps`, `checks`, `routings`, `pages`, `trash`, `requests`, `manage`) that needs the running app. Every act verb executes on first call and returns a receipt; the lane has no approval, waiting, or authority-mode state. A task may still be *waiting on an answer* — that is a state of its request record, not a held verb, and `chat wait`/`manage wait` settle on it and say so. `checks status` alone stays in the content-free read lane; Check enablement, runs, results, problems, and decisions are act-lane operations over explicitly designated files. The `manage` group is the management conversation above all Spaces: machine-local transcript, personal capabilities plus app-materialized management instructions, same turn machinery, full-trust (taught to prefer the CLI, not tool-restricted). `npm run work-fold:drive` is the separate real-Pi-turn test driver; do not conflate it with the installed management CLI.
- `npm run --silent work-fold:appearance` is the shared Codex/Claude Code primitive for creating, resolving, and validating inert Space-appearance proposals. It never applies a mutation; the person imports the typed file in Customize Space. Separately, `work-fold spaces appearance apply|reset|undo` is the act lane's journaled, undo-carrying application path for the same typed proposal while the app is running; the npm-script primitive stays inert and import-only. Keep its schema and safety boundary aligned with [Space customization](docs/space-customization.md).
- The harness-loading conventions are documented by [Codex](https://developers.openai.com/codex/guides/agents-md), [Codex Skills](https://developers.openai.com/codex/skills), [Claude Code memory](https://code.claude.com/docs/en/memory), and [Claude Code Skills](https://code.claude.com/docs/en/skills). Repository behavior is defined here.

## Product boundaries

- Use **work-fold** as the user-facing product name.
- A **Space** is a human-friendly working context backed by one ordinary folder. Registering an existing folder must not move, copy, or rename user files. work-fold deliberately maintains hidden, portable `.work-fold/space.json` identity metadata and `.work-fold/conversations/` logs in that folder.
- The folder is transparent infrastructure, not a proprietary container. Keep **Show folder** and normal filesystem interoperability intact.
- Use **Library** only for passive, reusable personal materials. Library items enter a Space through an explicit copy and never become Assistant context automatically.
- Use **Assistant tools** as the user-facing management surface and **Capability** as the internal umbrella. Inside it, use **Skill** for a reusable way of working and **Extension** for executable Pi capabilities or connections. Packages are distribution and lifecycle plumbing, not another top-level product concept.
- Treat `src/shared/product-identity.json` as the single brand-bearing identity contract. The product is `work-fold`, the package is `work-fold-desktop`, the production app id is `com.work-fold.desktop`, the local-smoke app id is `com.work-fold.desktop.local-smoke`, the updater cache is `work-fold-desktop-updater`, the internal scheme is `work-fold-desktop`, the CLI is `work-fold`, and product-owned environment variables use `WORKFOLD_*`.
- New product-facing technical contracts use `/api/spaces`, `x-work-fold-session`, `window.workFoldDesktop`, `work-fold.restricted-app-bridge`, and `globalThis.workFoldRestrictedApp`. App-platform records use `work-fold.app-release`, `work-fold.artifact.v1:sha256:*`, `application/vnd.work-fold.*`, and the identity fields `spaceId`, `sourceSpaceId`, and `targetSpaceId`; do not accept the legacy spellings as aliases.
- Keep provider credentials, Space registrations, History objects, Pi sessions, ignore rules, and machine-specific application state outside user content folders. Only the documented portable `.work-fold/` records belong in a Space.
- Treat project Pi resources—including `.pi` and other Pi-supported project locations—as executable configuration. Successfully creating or registering a Space is work-fold's authorization to load that folder's local Pi configuration; removing the Space revokes that work-fold authorization. Do not add a second trust prompt for the same act.
- Prefer Pi's built-in tools, resource loader, auth storage, model registry, package manager, skills, and extensions over app-specific replacements.
- Keep agent-created restricted apps in their separate reviewed-web lane. They use `agent-app.json`, digest-pinned installation, sandboxed Electron hosts, and narrow host brokers; they must never be installed through Pi's package manager or merged into Pi's loaded Extension catalog.
- Do not bundle proprietary tools, instructions, source libraries, or account integrations.
- Do not describe a desktop-synchronized folder as native cloud integration. Google Drive currently works through Google Drive for desktop; direct Drive APIs and native provider OAuth are future adapter work.

## Product rails

- **Local first:** a Space remains useful as a folder without an account or cloud service.
- **Understandable:** explain outcomes in terms of Spaces, Library materials, and Assistant tools; identify Skills and Extensions inside that surface, and reveal technical paths and package sources as supporting detail.
- **Explicit context:** registering a Space, adding or copying materials, installing packages, granting connections, and attaching files are distinct actions. Do not silently put files or capabilities into a conversation.
- **Understandable authorization:** creating or registering a Space authorizes its local Pi configuration without a redundant trust ceremony. Package review, connection secrets, and Chat context remain separate explicit acts; installing a Space app grants the powers its package declares ([Receipts, not gates](docs/receipts-not-gates.md), F21); and removing the Space must revoke work-fold's project-runtime authorization.
- **Portable identity:** `.work-fold/` is data, not executable configuration. Preserve a valid manifest id when a Space folder moves, hide `.work-fold/` and `.pi/` from Files, and exclude both from History capture.
- **Clean break:** work-fold never parses, imports, migrates, mutates, or deletes legacy Workspace application state or `.workspace/` metadata. Legacy metadata remains hidden and excluded from Files, History, Search, Check targets, and restricted-app grants, but it is non-authoritative. Managed deletion moves the claimed folder into Recently deleted rather than erasing it, and an entry whose tree contains `.workspace/` is held there: neither the retention window nor **Delete now** may erase it. Registration removal remains available without folder deletion. A new work-fold profile starts empty; Pi's personal resources and auth may remain shared at the configured Pi root, while work-fold sessions use their own `sessions/work-fold/` namespace.
- **Space-bound tabs:** every surface tab owns a Space id. Activating a tab activates that Space; switching Spaces restores that Space's most recent tab. Never make a tab silently inherit whichever Space happens to be selected.
- **Background continuity:** inactive Chat tabs stay mounted while their turns run. Tab switches, taskbar minimization, sleep/wake recovery, and close-to-tray must not cancel an accepted turn or lose its persisted result; only an explicit stop or quit may do that.
- **Native Pi compatibility:** preserve standard `SKILL.md` directories and Pi scopes. Do not fork a work-fold-only skill or extension format.
- **General computer work:** avoid code-only assumptions in primary UI copy and workflows.
- **Apps come up able to work:** installing a preview or a Release grants every declared network destination, file permission (a directory permission binds to the whole Space), notification category, and Check-result slot, and enables every declared automation; a code change carries forward connections whose destination declaration is byte-identical, automation enabled states by id, and run receipts. Revoke, disconnect, and disable are the person's narrowing controls, and revocation must stop stale launches before authority changes take effect. Secrets are entered by the person once per destination on the trusted surface; no task waits on that.
- **Receipts, not gates:** every product verb executes on first call and leaves a receipt. Verbs that make bytes runnable, widen a standing power, or destroy still pin their exact identities, journal before execution, recheck at effect time, execute at most once, and run through the same domain path as the desktop — as attribution and recovery, not as a gate. There is one authority mode and no approval card, standing rule, or toggle. Every destruction is reversible: History covers what it can, and everything it cannot goes to Recently deleted (the machine-local trash) with a retention window. Pairing, provider-secret entry, and remote-address enrollment remain setup surfaces rather than model/CLI verbs, and no task waits on them.
- **Requests, questions, and one result shape:** every accepted Assistant turn belongs to a durable machine-local request record ([the collaboration contract](docs/collaboration-contract.md), F25). Assistants hand each other one result shape — a plain-language summary, optional structured details, the files they chose, and an outcome of succeeded, partial, or failed — and ask a question instead of guessing. A question ends its own turn and one accepted answer continues it exactly once; a parent turn never sits on a child that is waiting, and the host starts at most one follow-up turn per settle batch within the request's limits. The same verbs serve the fold, a Space Assistant, an app's requested task, and any shell-capable agent on the CLI, with the same receipts and the same named limits. Request records never enter a Space folder: what reaches a Space Chat is its assignment, answers to its own questions, deliberately released payloads, and copied files.
- **Above-Space cadence:** agency on a schedule lives in Spaces. Above them, only declared deterministic routings run unattended (including explicitly enabled bounded folder-change triggers; see docs/fold-routings.md). `routings enable` is one receipted call that pins the declaration digest; a routing may also message the fold through its declared `fold` step and fill a closed set of host-resolved placeholders. Cross-Space work never runs inside a Space chat because Space transcripts travel; what enters a Space Chat from above is its assignment, explicitly released payloads, and answers to its own questions.

## Stable information architecture

The rail starts with **Files**, followed by **Chats** and **History**. The persistent Space-identity header owns switching Spaces plus the compact **Use existing folder**, **Create new Space**, and **Manage Spaces** actions; that menu remains available on built-in, management, and contributed-app surfaces. **Add**, **Shortcuts**, and **Settings** stay at the bottom. Add offers exactly three destinations: **Your Library**, one persistent Library tab for the selected Space; **Skills & Extensions**, the Space-owned Assistant tools work tab (discovery and management are the same place); and **Apps**, the Space-owned tab for apps built for that Space (apps are deliberately not part of Skills & Extensions, and **Build with Assistant** there seeds a fresh Chat with starter text rather than Add offering app building). Every Space may own one Library tab, and every such tab reads the same passive personal collection shared across all Spaces. The owning Space is the default copy target, but the person can explicitly choose any registered Space before copying. Assistant tools combines Skills and Extensions into Installed/Discover views under the visible title **Skills & Extensions**; package source, scope, type, load state, diagnostics, update, and removal remain visible inside it. The Installed view groups tools by where they live — **Everywhere** (the fold and every Space) above **This Space only** (stored in the Space folder) — and every install chooses that location once, in the review step, with the same fold-above-Spaces picture. Installed Space apps appear in their contributed rail region, while the Space-owned **Apps** work tab (reached from Add, the command palette, install confirmations, and App Studio; deliberately not part of Skills & Extensions) owns their grants, connections, named automations and run history, local data, update review, and removal, Assistant requests, and the receipts of the app's own model use. Model-provider connections, model selection, API-key, and provider-OAuth setup belong in **Settings → Assistant**, not in the rail. Provider credentials are machine-wide, while model selection is saved separately for each portable Space identity and for the fold; the fold choice governs the same management conversation in the menu bar and on the web. Restricted-app connection grants and OAuth setup belong with that app in the **Apps** tab. User-facing copy uses **Space**, **Library**, and **Assistant tools** (navigated to as **Skills & Extensions**) even where internal routes or types use `space`, `project`, `resource`, or `capability` as technical terms.

See [Assistant capabilities](docs/assistant-capabilities.md) for the scopes, trust model, Anthropic-compatible skill import behavior, package boundary, and distinction between Library materials and Pi resources.
Read [Restricted app runtime](docs/restricted-app-runtime.md) and [Restricted app authoring](docs/restricted-app-authoring.md) before changing `agent-app.json`, app proposals, sandbox hosts, bridges, brokers, credentials, storage, notifications, named automation scheduling, or contributed app navigation.

## work-fold management layer

- `WorkFoldKernel` is the shared in-process read authority for versioned Space context, registered Spaces, active Assistant/compaction tasks, and Pi capability snapshots. The renderer/local API and CLI must consume the same semantic source rather than recreate selection or catalog rules.
- Every query carries an explicit actor. An explicit Space id wins; otherwise context resolves to the deepest registered Space containing the actor's current directory; otherwise it resolves to none.
- Keep adapters thin. The CLI projection intentionally emits compact, content-free summaries, while domain services continue to own mutations, trust, filesystem policy, History, and concurrency controls.
- Protocol v1 under `%APPDATA%\work-fold\cli` is same-user coordination, not an authenticated caller boundary. It must remain read-only and content-free. Mutations belong exclusively to the separately versioned act lane, which requires the per-launch act token minted by the running interactive app, explicit `--space` selection on every Space-scoped write (the management-scope, Library, routing, `trash`, and `requests` families are deliberately Space-free; a trash entry records its source Space, and a request record pins the Space of each child at the moment that work is handed over), replayed-request protection, and a durable receipt per accepted action; keep those properties intact when extending it. Runnable-code, standing-power, and destruction verbs run immediately through the prepare, pin, journal-first, fenced execution path and return the receipt like any direct verb; failed or interrupted executions are never auto-retried; destruction is reversible through History or Recently deleted. The act facade cannot enter secrets, pair a browser, or enroll a remote address. Remote access administration, act-token/pairing machinery, and provider credentials remain setup-only and have no act verb.
- Start and finish kernel task records on every Assistant-turn and Chat-compaction path, including errors and abort cleanup. Never leave ghost tasks or let a capability mutation interrupt active work.
- The management conversation's menu-bar/tray popover is a separate sandboxed renderer with a dedicated narrow preload. Management attachments are bounded references, not copies; downstream `chat.send`, `files.add`, and Space create/register actions carry an explicit active management parent task id. Never infer request lineage from whichever turn happens to be running, and never report a request Done while a child is running, waiting on an answer, failed, lost, or stopped.
- Every accepted turn joins one durable request record under the state root's `requests/` directory — not an in-memory registry. Records survive restart, are reconciled against the turn journal and never re-dispatched, keep their questions and results by id, and are removed only by retention. `requests list|show` reads that graph; `chat report|ask|answer|handoff` write to it; `chat wait`/`manage wait` settle when the followed turn ends or when its task starts waiting, and say which. Delivery of a report, an answer, or a handoff is host-side and needs no fold model turn.
- Treat snapshot versions and `--json` output as compatibility contracts. Update implementation, adapters, tests, [the management guide](docs/management-layer.md), README, security, and privacy documentation together when they change.

## Development

- Use Node 22.19.0 or newer.
- Run `npm run check` after TypeScript changes.
- Run `npm test` before handing off behavior changes.
- Use the smallest verification lane that can catch the failure you are working on; do not make an installer during every inner-loop UI change.
- Run `npm run desktop:prepare` after Electron, packaging, or runtime-resource changes, and before handing off a desktop-integrated change. The composed package and installer commands already include it.
- GitHub CI runs on macOS and verifies `npm run check`, `npm test`, and `npm run desktop:prepare`. Windows packaging and publication are inactive and must not gate Mac work.
- Before public Mac publication, require successful CI for the exact release commit twice: once from the pushed `main` commit and once from its matching pushed source tag. A pushed candidate tag is immutable evidence. If either run fails, do not publish, move, reuse, or delete that tag; fix the cause, advance to a higher unique version, and create a new release commit and tag.
- `npm run desktop:package:smoke`, the slower Forge-based `npm run desktop:package`, and `npm run desktop:make` remain dormant manual Windows diagnostics only. Do not add them to CI, tag automation, or the active release procedure unless Windows distribution is deliberately reactivated and this contract is updated first.
- On macOS, use Node 24 and run `npm run desktop:make:mac` for the complete ad hoc structural smoke candidate. That lane uses `work-fold Local Smoke` with a separate bundle id and updater-disabled runtime; never rename or install it over `work-fold.app`. Use `npm run desktop:rc:mac` for an app-only Developer ID-signed/notarized interactive candidate, `npm run desktop:make:mac:release` for the complete signed distribution candidate, and `npm run desktop:release:mac` for guarded build-and-publish. Inspect interrupted work with `npm run desktop:release:mac:status` and use a `:resume` lane only while its source-bound artifact checkpoint validates. Signing commands require the Developer ID identity and notarization profile documented in `docs/macos-release.md`.
- When changing the management layer or CLI, run the kernel, adapter, protocol, broker, desktop-host, and packaging suites through `npm test`; add focused coverage for every new snapshot or command.
- Never commit provider keys, signing material, tokens, or generated user data.
- Reset the package version only immediately before the first public release candidate, as specified in the release runbooks, and never relabel an existing build or tag. Later fixes and rollback releases always use a higher unique version.
- The active public desktop lane is Apple-silicon macOS. Source commits and exact release tags belong in `Mat-Tom-Son/work-fold`; signed/notarized Mac artifacts and automatic updates belong only in `Mat-Tom-Son/work-fold-mac-releases`. The source repository does not need a GitHub Release for Mac publication. The legacy `Mat-Tom-Son/workspace` and `Mat-Tom-Son/workspace-mac-releases` repositories are frozen and must never receive work-fold commits, tags, artifacts, or updater metadata.
- Mac automatic updates preserve `com.work-fold.desktop` and `work-fold-desktop-updater`; the structural smoke uses `com.work-fold.desktop.local-smoke` and never contacts the production feed. Publish Mac artifacts only to `Mat-Tom-Son/work-fold-mac-releases` and do not create competing tag jobs.
- If an earlier ad hoc work-fold build causes repeated Keychain prompts, use `npm run desktop:reset:mac-safe-storage -- --yes --reopen` only after work-fold is fully quit. Never request the Safe Storage secret with `security ... -g`; that diagnostic can itself prompt. The reset may remove provider/restricted-app credentials but must preserve Spaces and ordinary app data.
- Keep personal PFX files outside the repository and use only the `WIN_CSC_LINK` and `WIN_CSC_KEY_PASSWORD` GitHub secrets. Do not reuse organization signing credentials.
- Keep README claims and the docs in sync with shipped behavior. In particular, do not claim native Google Drive, provider OAuth, package lifecycle controls, or public signing until the corresponding user path is verified.

The active verification and publication boundaries are documented in [macOS build and release lane](docs/macos-build.md) and [macOS release runbook](docs/macos-release.md). The dormant Windows references are retained in [Windows build](docs/windows-build.md) and [Windows releases and signing](docs/windows-release.md) for a future deliberate reactivation only. The control-plane boundary and real-agent driver are documented in [work-fold management layer](docs/management-layer.md).


## Bounded text Checks and folder observation

The built-in text-review Check accepts one reviewed `criteria` rubric and explicit primary/reference UTF-8 targets; it uses the fold's model without the fold transcript, general tools, or edits. Preserve quote/digest admission, source-pinned sensor authority, visible provider-use limits, and failure-as-health semantics. Desktop setup and CLI use the same Check service. Routing folder observation is an explicit v3 declaration enabled by one receipted call, with bounded selectors, debounce, cooldown, and visible health. It rebaselines after startup/wake and pauses during routing work without replay; cross-Space handoffs remain ordered steps in one routing. Do not silently turn it into an ambient or durable event bus. App `assistant.infer` reuses the same bounded model transport with its own instructions and no evidence admission; it is not a Check and never becomes one.
