# Workspace 0.6.0

Workspace 0.6.0 adds the first working management surface above all Spaces: an
installed command lane that agents can use to inspect and operate Workspace,
plus one machine-local management conversation built on the same Pi turn
runtime as ordinary Space Chats.

## Operate Workspace through one installed command

- The existing content-free `workspace` read lane is joined by a separately
  versioned act lane for creating and registering Spaces, adding outside files
  with a History restore point, and creating, sending, inspecting, awaiting,
  and aborting Space Chats.
- Every accepted act request is journaled and flushed before its operation
  runs. A per-launch token binds commands to the currently running interactive
  app, replayed request ids are refused, and damaged receipt ledgers fail
  closed rather than risking a duplicate operation.
- `chat send` returns a task id. Task-scoped `status`, `result`, and `wait`
  follow that exact accepted turn to success, failure, or abort instead of
  confusing a previous transcript response with the new task's outcome.
- The Windows installer exposes the command through its current-user `PATH`.
  The Mac bundle exposes the same command to Pi child processes from
  `Workspace.app/Contents/bin` without silently changing shell profiles.

## One management conversation above Spaces

- `workspace manage send|status|result|wait|abort|list` reaches a distinct
  conversation scope above every Space. Its transcript lives in application
  state because it describes this computer's machine-local Space registry.
- The scope loads personal Pi capabilities plus an app-owned `AGENTS.md` and
  `manage-workspaces` Skill. Those resources teach it to inventory Spaces,
  place material through restore-pointed commands, delegate in-Space work to
  each Space's own Assistant, and report task-specific outcomes.
- The instructions are required. If Workspace cannot safely materialize them,
  the desktop and ordinary Spaces can still start, but management commands
  remain unavailable rather than running an unidentified, uninstructed agent.
- The default remains one management conversation; `--new` explicitly starts
  an additional thread when one is wanted.

## Native file drops and atomic additive placement

- Files dragged from the operating system onto any Chat composer upload into
  that Space's dated `Dropped/` folder and become explicit context for the
  message being composed.
- Multi-file uploads and multi-item Library copies roll back files already
  placed if a later item fails. CLI `files add` also undoes placement if its
  additive History checkpoint cannot be committed.
- Dropped-file and Library copy-in checkpoints remain targeted: undo removes
  only the paths created by that action and does not rewind unrelated Space
  work.

## Authorization boundaries and known limitations

The act token is an app-run binding inside a personal, same-operating-system-
user trust boundary; it is not authentication between different local users.
Act commands require the interactive app and do not provide a headless agent
runtime. Space-targeted writes always name a Space explicitly, and receipts
contain command metadata rather than prompt or file content, although bounded
request and response files briefly carry Chat content while a command runs.

The management conversation is a full-trust Pi Assistant, taught rather than
caged. It retains ordinary local file and shell tools and is instructed to
prefer the `workspace` commands for cross-Space work because those commands
carry Workspace's trust, conflict, History, and receipt rules. This release
does not claim an enforced CLI-only sandbox. It also does not add a desktop or
web tab for management; the shipped surface is CLI-first. Task outcomes remain
available for the current app run, while the conversation transcript remains
durable.

## Upgrade notes

This is an in-place update. Registered Spaces, named Chats, ordinary files,
Library materials, History, Pi resources, provider credentials and selection,
appearance settings, restricted apps and their reviewed digests, grants,
connections, automations, app data, Releases, and App Instances are preserved.
No manifest or user-data migration is required. Workspace creates the
machine-local management instruction and conversation folders when the new
scope is first prepared.

## Release verification posture

Public release completion requires the exact pushed `v0.6.0` commit to pass
dependency installation, TypeScript checks, the complete test suite,
high-severity dependency audit, desktop preparation, the real-Electron
restricted-app probe, and the canonical unpacked Windows package workflow.
The management dogfood must additionally complete a real provider-backed
identity turn and a create → place → delegate → task-scoped wait → report loop
through the agent-facing CLI. macOS publication additionally requires the
guarded Developer ID-signed, notarized, stapled release lane after the matching
source release is public.
