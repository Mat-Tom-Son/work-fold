# Workspace 0.7.0

Workspace 0.7.0 adds optional, evidence-backed **Checks**: small durable
expectations over files a person explicitly designates. Checks are powered by
the management layer and installed CLI, stay out of the main interface, and do
nothing in Spaces where they have not been deliberately configured.

## Teach Workspace one bounded expectation

- A person or Assistant can create an inert, reviewable
  `workspace.check-proposal` JSON file. Creating a proposal does not enable,
  run, schedule, or widen a Check.
- Enablement is a separate authenticated and receipted action naming one exact
  Space. The portable declaration below `.workspace/checks/` remains code-free
  data; the matching authority is machine-local and bound to the exact
  declaration, sensor revision, execution kind, and reviewed implementation
  digest.
- Enabling the same proposal again reuses the existing Check instead of
  minting a duplicate. A changed declaration or sensor implementation loses
  its old authority until it is explicitly enabled again.
- The first installed sensor, `workspace.file-presence@1`, verifies that exact
  primary files are present or absent. It works across ordinary file types
  because it checks path state without reading file contents.
- The shared authoring helper can create and validate the same inert proposal
  from Codex, Claude Code, or a terminal:

  ```bash
  npm run --silent workspace:checks -- create-file-presence \
    --title "Signed delivery exists" \
    --file "Delivery/signed.pdf" \
    --expect present \
    --out signed-delivery.workspace-check.json
  ```

## Run and review through the management layer

- `workspace checks status --space ...` exposes only aggregate, content-free
  state. `not-configured` means unknown, not healthy, and Workspace does not
  inspect an unconfigured Space to calculate it.
- Authenticated `enable`, `disable`, `run`, `task`, `result`, `wait`, `abort`,
  `problems`, and `decide` commands use explicit Space scope, the per-launch
  act token, journal-first at-most-once handling, durable receipts, and
  task-scoped outcomes.
- The management conversation is taught the same workflow. A one-off request
  to inspect files remains ordinary Chat work; durable behavior requires clear
  intent such as “keep checking” or “watch this,” followed by proposal review
  and a separate explicit enable instruction.
- Every surfaced finding carries typed evidence that the host independently
  re-verifies against current designated targets. Stale evidence is
  invalidated; skipped input, malformed evidence, exhausted limits, missing
  capabilities, and failed runs remain Check-health problems instead of being
  misreported as problems in a person's files.
- `accept`, `reject`, `resolve`, and time-bounded `defer` decisions are scoped
  to one finding fingerprint. A successful clear run consumes decisions that
  would hide a later recurrence, so a fixed file that goes missing again
  returns to **Needs attention** rather than becoming a permanent false clear.

## Bounded and fail-closed by construction

- Targets are exact Space-relative files or explicitly bounded directory
  selectors with declared recursion and file extensions. The first sensor uses
  exact files only; the neutral contract and admission boundary are ready for
  later tree-capable sensors.
- Resolution rejects path escapes, symbolic links and junctions, special
  files, `.workspace/`, `.pi/`, Windows device/alias ambiguity, and targets
  that enter another registered Space. Enumeration, file size, total bytes,
  findings, stored records, output, and runtime are all bounded.
- Sensors receive a closed runner-owned projection, not reopenable absolute
  paths. Candidate findings cannot surface unless their target and evidence
  remain inside the declaration's exact file or bounded tree membership.
- Check runs participate in the internal Workspace task and capability-lock
  lifecycle. Space removal and Space-registry changes take inverse leases so
  target ownership, evidence access, authority cleanup, and run terminalization
  cannot race each other.
- Machine state uses bounded no-follow reads, atomic replacement, guarded
  backup recovery, and parse-free removal. Backup recovery strips grants;
  damaged or future-version state fails closed without blocking Space removal.
- Accepted and running work reports as pending, never as an infrastructure
  failure. Bounded problem results disclose truncation in both JSON and human
  output instead of silently undercounting.

## Deliberately deferred

Checks remain an experimental management/CLI capability in this release.
There is no permanent rail item, Space-header badge, work tab, background
watcher, schedule, notification, model-backed sensor, automatic fix, or gate
over other work. The initial sensor does not inspect text, dates, totals,
citations, images, or document structure. Those layers can be added only after
real dogfooding demonstrates precise findings, and they must reuse the same
proposal, authority, bounded-target, evidence-admission, task, and receipt
boundaries.

## Upgrade notes

This is an in-place update. Existing Spaces are not scanned and gain no Check
authority. A Space without enabled Checks behaves exactly as before. Portable
Check declarations already present in a registered folder are discovered only
as inert proposals; registration never enables them. Machine-local Check state
is created outside the Space only when the feature is used.

Registered Spaces, ordinary files, Chats, management conversations, History,
Library materials, Pi resources, provider credentials and selection,
appearance, restricted apps and their grants/connections/automations/data,
App Projects, Releases, and Instances are preserved. No existing manifest or
user-data migration is required.

## Release verification posture

The feature was reviewed independently for product fit, architecture, race
safety, and adversarial failure modes. A second Claude Desktop review found a
recurrence-lifecycle blocker; the durable-state fix and all adjacent hardening
then received a fresh source review and a **SHIP** verdict. The final source
gate covers TypeScript checks, 642 tests (641 passing and one expected
Windows-only skip), a high-severity dependency audit, desktop preparation, the
real-Electron restricted-app sandbox probe, and the canonical unpacked Windows
package. Public Windows and macOS artifacts must still pass their independent
tagged CI, signing, notarization, stapling, checksum, manifest, and feed
verification lanes before this release is complete.
