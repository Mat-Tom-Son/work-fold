# Workspace 0.7.1

Workspace 0.7.1 is a narrowly scoped correction to the experimental Checks
status summary. An enabled Check that has not completed its first manual run
now reports through the explicit `neverRun` aggregate instead of being counted
as `stale`. `stale` remains reserved for a previous result whose designated
inputs have changed.

The Space-level state remains `stale` until a requested run establishes current
evidence. This preserves the fail-closed rule that unknown Check health is never
presented as healthy while making the reason visible to the management layer and
`workspace checks status` consumers.

## Boundaries remain unchanged

- Checks are still optional, experimental, and absent from the Workspace
  frontend. This patch adds no rail item, header indicator, work tab, or other
  Checks UI.
- Runs remain manual. There is no background watcher, schedule, notification,
  automatic fix, model-backed sensor, or gate over other work.
- Creating or discovering a portable Check declaration does not enable it.
  Enablement remains a separate authenticated, receipted action for one exact
  Space and declaration digest.
- The initial `workspace.file-presence@1` sensor still evaluates only the
  presence or absence of explicitly designated files. It does not inspect file
  contents or broaden target authority.

## Upgrade notes

This is an in-place patch update with no manifest or user-data migration.
Existing Spaces, declarations, enablement grants, run history, findings,
decisions, Chats, History, Library materials, Pi resources, credentials,
restricted apps, and app data are preserved.

Previously stored Check results are not rewritten. The corrected aggregate is
computed when status is requested: enabled Checks with no prior run contribute
to `neverRun`, while a prior result with changed inputs contributes to `stale`.
Spaces without enabled Checks behave exactly as before and are not scanned.

## Known limitations

Checks remain a management/CLI capability rather than a frontend feature. The
aggregate schema is experimental, Check runs must be requested explicitly, and
the first sensor covers file presence only. Richer content sensors, schedules,
notifications, gates, and frontend surfaces remain deferred.

## Release verification posture

The patch is covered by service, adapter, protocol, JSON, and human-output tests
that distinguish never-run Checks from changed prior results and reject
inconsistent aggregates. The release gates use Node 24 and include a clean
dependency install, TypeScript checks, the complete test suite, a high-severity
dependency audit, desktop preparation with the real-Electron restricted-app
probe, packaged artifact verification, and whitespace validation. Public
Windows and macOS artifacts must additionally pass their tag/version, signing,
notarization, stapling, checksum, manifest, digest, feed, and public-release
checks before publication is accepted.
